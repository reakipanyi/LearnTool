# 安全代码修改技能

在进行任何代码修改时，必须严格遵循以下三大原则：
1. **保护原有注释**：不得删除未涉及变更的代码注释
2. **保留文件编码**：不得修改文件编码格式导致乱码
3. **修改后审查**：每次修改完成后必须进行代码审查

---

## 一、注释保护规范

### 核心原则

- **绝对禁止**在未确认的情况下删除任何注释（包括被注释掉的代码和说明性注释）
- 修改代码时，保留相关的原始注释
- 即使注释看起来过时或错误，也不要直接删除，先标记为待确认

### 何时可以修改注释

只有在以下情况才可以修改注释：
- **逻辑变更**：代码逻辑发生变化，原注释已与新逻辑不符
- **用户明确要求**：用户明确要求修改或删除特定注释
- **明显错误**：注释存在明显的事实错误且会造成误导

### 注释修改原则

- **最小修改**：只修改与逻辑变更直接相关的注释部分
- **保留风格**：保持原有的注释风格和格式
- **更新而非删除**：优先更新注释内容，而不是直接删除
- **标记待确认**：不确定时保留原注释，可添加 `// TODO: 确认是否需要更新` 标记

### 具体操作规范

#### 修改代码时
```
修改前先读取完整上下文（包括注释）
old_string 必须包含相关注释
new_string 中保留原有注释，仅更新与代码变更相关的部分
确保注释与代码的对应关系不变
```

#### 重构代码时
- 移动代码块时，连同相关注释一起移动
- 拆分函数时，将对应注释拆分到新函数中
- 合并代码时，合并相关注释并去重

#### 修复 bug 时
- 保留 bug 相关的历史注释（作为历史记录）
- 添加修复说明注释，而不是替换原注释
- 原注释错误时，保留并修正，不要删除

### 注释保护检查清单

每次代码修改完成后，检查：
- [ ] 原有注释是否完整保留
- [ ] 注释代码（被注释掉的代码）是否被误删
- [ ] 新增代码是否需要补充注释（但不强制）
- [ ] 修改的注释是否与逻辑变更对应
- [ ] 是否存在无理由删除注释的情况

### 反模式（禁止）

❌ 因为"注释过时"就直接删除
❌ 重写整个函数时清空所有注释
❌ 移动代码时丢失关联注释
❌ 用自己的注释风格替换原作者的注释
❌ 删除被注释掉的代码（除非用户明确要求）

## 二、文件编码保护规范

### 核心原则

- **绝对禁止**修改文件的原始编码格式
- 读取和写入文件时必须保持编码一致
- 遇到编码问题时，先确认再处理，不得擅自转换

### 编码检测与确认

#### 修改前检查
1. 确认文件当前的编码格式（UTF-8、GBK、GB2312、ISO-8859-1 等）
2. 检查文件是否包含 BOM（Byte Order Mark）
3. 确认文件的换行符格式（CRLF、LF、CR）

#### 如何检测编码
- 使用编辑器或 IDE 的状态栏查看编码信息
- 使用命令行工具检测（如 `file` 命令）
- 注意中文注释、特殊字符的显示是否正常

### 编码保护操作规范

#### 读取文件时
- 必须使用文件原始编码读取
- 不得自动转换编码
- 如果读取出现乱码，停止操作并确认正确编码

#### 写入文件时
- 必须使用与读取时相同的编码写入
- 保持原有的 BOM 状态（有 BOM 的保留，没有的不添加）
- 保持原有的换行符格式
- 不得自动格式化或重新编码整个文件

#### 使用 Edit 工具时
- old_string 必须与文件中的内容完全一致（包括编码）
- new_string 的编码必须与 old_string 一致
- 不得在替换过程中改变任何字符的编码表示

### 常见编码问题处理

#### 问题1：读取时出现乱码
**处理方法**：
1. 立即停止操作
2. 尝试其他常见编码（GBK、UTF-8、GB2312）
3. 确认正确编码后再继续
4. 不要基于乱码内容进行修改

#### 问题2：中文注释显示异常
**处理方法**：
1. 检查文件编码是否与编辑器设置匹配
2. 确认不是字体渲染问题
3. 不要擅自转码，先确认原始编码

#### 问题3：换行符不一致
**处理方法**：
1. 保持原文件的换行符格式
2. 新增内容使用与原文件一致的换行符
3. 不要批量转换换行符

### 编码保护检查清单

每次代码修改完成后，检查：
- [ ] 文件编码是否与修改前一致
- [ ] BOM 是否保持原状
- [ ] 换行符格式是否一致
- [ ] 中文及特殊字符是否正常显示
- [ ] 文件大小是否异常变化（可能暗示编码变化）

### 反模式（禁止）

❌ 擅自将 GBK 文件转为 UTF-8
❌ 自动添加或移除 BOM
❌ 批量转换文件编码
❌ 在乱码状态下继续修改
❌ 用 Write 工具完全重写文件（除非用户明确要求）

## 三、修改后代码审查规范

每次代码修改完成后，必须立即对本次修改进行自我审查。

### 审查原则

1. **功能优先原则**：修改不得破坏现有功能
2. **逻辑不变原则**：除非是 bug 修复，否则不得改变原有业务逻辑
3. **最小变更原则**：只修改必要的部分，不做无关改动

### 审查流程

#### 第一步：变更范围检查
- [ ] 本次修改的文件数量是否符合预期
- [ ] 是否修改了不应该修改的文件
- [ ] 每个文件的修改范围是否最小化
- [ ] 是否存在意外的空白字符变化

#### 第二步：功能完整性检查
- [ ] 修改是否改变了函数/方法的返回值？
- [ ] 修改是否影响了异常处理流程？
- [ ] 修改是否改变了边界条件的处理方式？
- [ ] 修改是否删除或修改了调用方依赖的接口？
- [ ] 修改是否影响了并发/异步执行的时序？

#### 第三步：业务逻辑一致性检查
- [ ] 我是否完全理解了这段代码的业务意图？
- [ ] 修改是否改变了业务规则的判断条件？
- [ ] 修改是否改变了数据流转的顺序或内容？
- [ ] 修改是否改变了状态机的状态转换逻辑？
- [ ] 修改是否考虑了所有分支路径（包括异常路径）？

#### 第四步：边界与异常检查
- [ ] 修改是否考虑了空值（null/none/nil）情况？
- [ ] 修改是否考虑了空集合、空字符串等边界情况？
- [ ] 修改是否考虑了数值溢出、除零等数学异常？
- [ ] 修改是否保持了原有的错误处理和日志记录？
- [ ] 修改是否会引入新的未捕获异常？

#### 第五步：注释保护检查
- [ ] 原有注释是否完整保留？
- [ ] 是否误删了被注释掉的代码？
- [ ] 修改的注释是否与逻辑变更对应？
- [ ] 是否存在无理由删除注释的情况？

#### 第六步：编码保护检查
- [ ] 文件编码是否保持不变？
- [ ] 中文及特殊字符是否正常？
- [ ] 换行符格式是否一致？

### 问题分级

根据发现的问题严重程度，分级处理：

#### P0 - 严重问题（必须修复）
- 功能被破坏
- 业务逻辑被错误改变
- 引入了明显的 bug
- 注释被误删且无法恢复
- 文件编码被改变导致乱码

#### P1 - 潜在问题（建议修复）
- 边界条件处理不完整
- 异常处理不够健壮
- 代码可读性下降
- 注释与代码不完全对应

#### P2 - 优化建议（可选修复）
- 代码风格可以改进
- 命名可以更清晰
- 结构可以更合理

### 审查输出模板

```
【修改审查报告】
修改文件：[文件列表]
变更类型：[bug修复/功能新增/重构/优化]
审查结果：[通过/需修复]

【P0 严重问题】
- [问题1描述]
- [问题2描述]

【P1 潜在问题】
- [问题1描述]
- [问题2描述]

【P2 优化建议】
- [建议1描述]
- [建议2描述]

【注释保护检查】
- 原有注释保留：[是/否/部分]
- 误删注释：[有/无]
- 注释更新合理性：[合理/待确认]

【编码保护检查】
- 文件编码保持：[是/否]
- 中文显示正常：[是/否]
- 换行符一致：[是/否]

【总结】
[简要总结审查结果，是否需要修复后再提交]
```

## 四、完整工作流程

每次代码修改必须遵循以下完整流程：

### 第一步：修改前准备
1. 确认文件编码格式
2. 读取完整文件内容（包括注释）
3. 理解代码逻辑和业务意图
4. 明确修改目标和范围

### 第二步：执行修改
1. 使用最小变更原则
2. 保护所有未涉及的注释
3. 保持文件编码不变
4. 记录修改的内容

### 第三步：修改后审查
1. 运行注释保护检查清单
2. 运行编码保护检查清单
3. 运行代码审查流程
4. 生成审查报告

### 第四步：问题处理
- 发现 P0 问题：立即修复
- 发现 P1 问题：评估后修复或标记
- 发现 P2 问题：可选优化，不强制
- 全部通过：修改完成

## 五、自检口诀

修改前默念：

> **先看编码再读全，注释保护记心间。**
> **最小变更是原则，改完审查不能免。**

修改后默念：

> **一改功能二改逻，三改边界四改错。**
> **注释编码都保住，安全修改才合格。**
