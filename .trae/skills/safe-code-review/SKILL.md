# 安全代码审查技能

## 核心原则

在提出任何代码审查建议前，必须遵循以下铁律：

1. **功能优先原则**：任何建议都不得以牺牲现有功能为代价
2. **逻辑不变原则**：优化重构不得改变原有业务逻辑的输入输出行为
3. **验证前置原则**：提出建议前，必须在脑海中或实际验证建议的正确性

---

## 审查建议自检清单（必查）

在输出每一条修改建议前，逐项检查以下问题：

### 一、功能完整性检查

- [ ] 我的建议是否会改变函数/方法的返回值？
- [ ] 我的建议是否会影响异常处理流程？
- [ ] 我的建议是否会改变边界条件的处理方式？
- [ ] 我的建议是否会删除或修改调用方依赖的接口？
- [ ] 我的建议是否会影响并发/异步执行的时序？

### 二、业务逻辑一致性检查

- [ ] 我是否完全理解了这段代码的业务意图？
- [ ] 我的建议是否改变了业务规则的判断条件？
- [ ] 我的建议是否改变了数据流转的顺序或内容？
- [ ] 我的建议是否改变了状态机的状态转换逻辑？
- [ ] 我的建议是否考虑了所有分支路径（包括异常路径）？

### 三、边界与异常检查

- [ ] 我的建议是否考虑了空值（null/none/nil）情况？
- [ ] 我的建议是否考虑了空集合、空字符串等边界情况？
- [ ] 我的建议是否考虑了数值溢出、除零等数学异常？
- [ ] 我的建议是否保持了原有的错误处理和日志记录？
- [ ] 我的建议是否会引入新的未捕获异常？

### 四、兼容性检查

- [ ] 我的建议是否改变了公共 API 的签名？
- [ ] 我的建议是否改变了数据结构的字段含义？
- [ ] 我的建议是否影响了与其他模块的交互协议？
- [ ] 我的建议是否考虑了向后兼容性？
- [ ] 我的建议是否会导致配置文件格式变化？

## 建议分级标准

根据建议的风险等级，采用不同的表述方式：

### P0 - 确定性 Bug（高风险）
**特征**：代码明显存在错误，一定会导致功能异常
**表述方式**：明确指出问题 + 复现路径 + 正确逻辑

### P1 - 潜在问题（中风险）
**特征**：在特定条件下可能出问题，或逻辑不够严谨
**表述方式**：指出风险场景 + 询问是否为预期行为 + 建议方案

### P2 - 代码优化（低风险）
**特征**：不影响功能，但可读性、性能、可维护性可提升
**表述方式**：以"建议/可以考虑"开头 + 说明优化收益 + 提供方案

### P3 - 风格偏好（无风险）
**特征**：纯风格、命名、格式等主观偏好
**表述方式**：明确标注为"个人偏好/风格建议" + 不强求修改

## 提出建议的标准流程

### 第一步：理解代码

1. 阅读函数/模块的完整上下文
2. 理解输入、输出、副作用
3. 识别业务规则和关键逻辑
4. 查看相关的调用方和被调用方

### 第二步：分析改动

1. 明确代码改动的意图
2. 识别改动影响的范围
3. 思考可能的回归风险
4. 检查是否有对应的测试覆盖

### 第三步：形成建议

1. 用自检清单逐项验证建议
2. 给建议标注风险等级（P0-P3）
3. 思考建议的可执行验证方法
4. 用清晰、尊重的语言表述

### 第四步：反向验证

在提交建议前，问自己：
- 如果我是作者，我能理解这条建议吗？
- 如果按照建议修改，会引入新问题吗？
- 我是否遗漏了某些上下文信息？
- 这条建议的价值是否大于修改成本？

## 常见的不合理建议陷阱

### 陷阱1：过度优化
**表现**：为了微小的性能提升或代码简洁，改变了清晰的业务逻辑
**避免方法**：
- 优先保证可读性和正确性
- 没有性能数据支撑时，不提性能优化建议
- 重构建议必须保持行为等价

### 陷阱2：忽视业务上下文
**表现**：从纯技术角度提出建议，但不了解业务背景
**避免方法**：
- 不确定时，先提问而不是直接建议
- 用"这里为什么这样处理？"代替"这里应该改成..."
- 尊重原作者的业务判断

### 陷阱3：改变错误处理语义
**表现**：修改异常捕获、错误返回方式，导致上层调用方出错
**避免方法**：
- 检查所有调用方的错误处理方式
- 确认异常类型和错误码的契约
- 涉及错误处理的改动必须慎之又慎

### 陷阱4：修改边界条件
**表现**：简化边界判断，看似更优雅，实则漏掉了某些情况
**避免方法**：
- 找出所有边界条件的来源
- 思考每个边界条件背后的业务原因
- 不确定时，宁可不改

### 陷阱5：滥用设计模式
**表现**：为了用模式而用模式，增加不必要的复杂度
**避免方法**：
- 简单问题用简单方案
- 设计模式是为了解决问题，不是为了炫技
- 考虑团队成员的理解成本

## 安全建议模板

### 发现问题类

```
【问题等级】P0/P1/P2/P3
【问题描述】简要描述问题
【影响范围】说明可能影响的功能或模块
【复现条件】在什么情况下会触发问题
【建议方案】修改建议（如果有）
【验证方法】如何验证修改是正确的
```

### 提问确认类

```
【确认事项】想确认的问题
【我的理解】我对这段代码的理解（可能有误）
【疑问点】具体哪里有疑问
【背景信息】我看到的相关上下文
```

### 优化建议类

```
【优化类型】可读性/性能/可维护性/其他
【当前代码】现有实现方式
【建议方案】建议的实现方式
【优化收益】这样改的好处
【潜在风险】可能的风险点（如有）
【是否必须】建议标注为可选或必须
```

## 验证建议正确性的方法

在提出建议前，可以通过以下方式验证：

### 1. 代码走查
- 手动模拟代码执行路径
- 检查各种输入情况下的输出
- 验证所有分支的逻辑正确性

### 2. 测试用例思维
- 思考这段代码应该有哪些测试用例
- 我的建议是否能通过原有测试用例
- 是否需要补充新的测试用例

### 3. 反向思考
- 如果我的建议是错的，可能错在哪里？
- 有哪些场景我没有考虑到？
- 原作者为什么那样写？有什么我没看到的原因？

### 4. 影响面分析
- 修改会影响哪些调用方？
- 上下游模块是否需要同步修改？
- 数据结构变化是否影响持久化数据？

---

## 代码审查的正确姿势

1. **先肯定，再建议**：好的地方先说，建设性意见后说
2. **对事不对人**：评论代码，不评论人
3. **提供上下文**：解释为什么建议这样改，而不是只说改什么
4. **给选择空间**：多种方案都可行时，列出选项供作者选择
5. **承认不确定性**：不确定的地方明确说"我不确定，但..."
6. **关注重要问题**：不要在小风格问题上纠结，重点关注功能和逻辑
7. **理解业务背景**：技术决策往往有业务驱动因素，先理解再评论

## 自检口诀

提出建议前默念：

> **一改功能二改逻，三改边界四改错。**
> **先问自己为什么，再想作者为何做。**
> **不确定时先提问，有把握时再建议。**
> **功能正确是底线，代码优化放其次。**
