# 连连看 设计方案

> 项目：LearningAssistant（WinForms + WebView2）
> 目标：在现有"单词消消乐""记忆翻牌"基础上，新增一款 **"连连看"（Link / Connect）** 游戏：在格盘上连连"单词 ↔ 释义"配对，且**两点之间必须存在不超过 2 次转弯的空路径**才能消除。
> 本文档只做方案设计，不涉及代码实现。

---

## 1. 背景与目标

"单词消消乐"（配对消除）与"记忆翻牌"（记忆配对）已打通 WebView2 静态页 + 内容编辑器数据 + 成绩回写的闭环。两者都是**逐张点选配对**，缺少一款考验**路径规划与布局观察**的玩法。

本方案设计 **"连连看"**：
- 复用消消乐/翻牌已验证的整套技术路径（`WebView2GameFormBase` + `WordMatchGameService` + 成绩回写）；
- 玩法核心差异：**配对必须满足可达路径（≤2 次转弯）**，考验玩家读盘与路线规划；
- 纯静态网页（HTML + CSS + JS），无第三方框架。

---

## 2. 玩法设计

### 2.1 核心规则（连连看 / Link）
在 M×N 网格盘面上放置若干张卡片（**正面朝上**），每张卡片是某词条的"单词"或"释义"。玩家依次点击两张卡片：
- **配对成功条件（两条同时满足）**：
  1. 两张卡片**互为配对**（一张单词 + 一张释义，属于同一词条，按局内 key 匹配）；
  2. 两张卡片之间存在一条可擦除路径：路径只能经过空位，且**转弯次数不超过 2 次**（经典连连看规则）。
- **配对成功**：两张卡片消除（渐隐/缩放），得分。
- **不满足任意一条**：视为无效点选，提示原因（不配对 / 路径不通），不消除。

### 2.2 配牌与盘面
- 每局抽取 **N=10** 对（20 张卡），盘面建议 **5×4**（10 列自适应用 4 行布局）。
- 抽词策略：复用 `WordMatchGameService.BuildItems(..., selection)`，默认 `WrongFirst`（错题优先），同记忆翻牌。
- **盘面生成必须保证"开局可解"**：避免所有配对初始即被阻断；生成后可做一次"可解性校验 + 重排"（见 4.4）。
- **死局检测**：当任意一对都无法消去时，前端提示"重新洗牌"按钮（重新排列当前词卡），不重新抽词也可。

### 2.3 计分与反馈
- 计分：基础分 + **连击**（连续消除成功加分）− 无效点选小惩罚（可选）。
- 路径在点选两张后**高亮显示**（边框/线段示意），帮助玩家理解"为什么通 / 为什么不通"。
- 消除反馈：卡片淡出 + 成功音效；无效反馈：抖动 + 提示原因。
- 发音：点击单词卡可 `speechSynthesis` 朗读。

### 2.4 通关与结算
- 全部 N 对消除 → 结算页：得分、用时、步数、错误尝试、最高连击、星级。
- 结算星级参考：用时 + 无效点选次数综合评定。
- "再来一局"（同组重排）/ "换一组"（重新抽词，走 `restart` 消息让宿主重发数据）。

## 3. 数据接入方案

### 3.1 复用现有服务（几乎零新增后端）
- **取词**：复用 `WordMatchGameService.BuildItems(context, maxCount, selection)`，返回 `List<WordMatchItemDto>`（含 `Id / Word / Meaning / Phonetic`）。
- **成绩回写**：复用 `WordMatchGameService.ApplyResults(userId, context, results)`。
- **宿主**：新增 `LinkMatchGameForm`，继承 `WebView2GameFormBase`，复用其 `restart` 补发、`gameEnd` 上报、主题联动、camelCase 序列化。

### 3.2 成绩回写语义
- 每个词条记为一条结果；配对成功即 `Correct = true`。
- 连连看**没有"错误配对保留"**的中间态（配对失败不会像翻牌那样翻回），因为卡片正面常显。为贴合复习语义：
  - 若该词条曾在玩家的一个"已提交配对"中被明确提示"不配对"（点击过但未消除）→ `Correct = false`；
  - 否则 `Correct = true`。
- 前端在消除成功时上报该词条 id 与其 `correct` 标记；无效点选只做屏内提示。

### 3.3 宿主窗体
新增 `LinkMatchGameForm`，与记忆翻牌结构一致，仅替换：
- `FormTitle` → "🔗 连连看"；
- `HtmlFileRelativePath` → `Resources/LinkMatchGame/index.html`；
- `BuildData` → `BuildItems(context, 10, WordSelection.WrongFirst)`。

## 4. 前端页面设计（静态 HTML）

### 4.1 文件组织
```
Resources/LinkMatchGame/
  index.html     # 页面骨架 + 布局
  style.css      # 格盘、路径高亮、消除动效、明暗主题
  game.js        # 配牌、路径判定、消除、计分、结算、通信
```
- 纯原生 JS，无外部依赖/CDN，离线可用；支持 `?mock=1` 内置示例数据。

### 4.2 页面布局
- 顶部：标题、得分、连击、步数、计时、"换一组/重新洗牌"。
- 中部：卡片格盘（CSS `grid`，如 5×4，卡片圆角/多彩渐变，正面常显）。
- 底部工具条：当前提示（"点击两张互为配对的卡片"）、"洗牌"按钮。

### 4.3 卡片
- 卡片正面常显：单词卡（词 + 音标 + 🔊）走冷色系，释义卡走暖色系（复用记忆翻牌配色）。
- 状态类：`idle` / `selected`（第一张选中高亮）/ `matched`（已消除）/ `invalid`（无效点选抖动）。
- 明暗主题：`body[data-theme]` 控制，与 WinForms 联动。

### 4.4 路径判定算法（核心）
经典连连看 ≤2 次转弯判定，在**格点（card 网格）上**：
1. 将盘面视为网格，空格与卡片格均为节点；路径起点、终点是两张卡各自相邻空格的虚拟出口。
2. **0 转**：同一直线上相邻可达（起点紧邻终点）。
3. **1 转**：两卡共用一个"拐角空位"（起点的行 + 终点的列，或 起点的列 + 终点的行），且该空位到两端均可达。
4. **2 转**：起点行沿某列到空位 A，空位 A 横向到空位 B，空位 B 沿列到终点——枚举起点、终点的所有可达行列，检查是否有一条"横-竖-横"或"竖-横-竖"连通。
5. **边界穿越**：允许路径从盘面外边缘穿过（经典连连看允许绕边界），可选开启。

> 判定要点：全程只走空位；同格卡自身占用不可穿过。为简化，首版可**不允许**绕盘外边缘，仅允许盘内空路径。

**开局可解校验**：洗牌后，检查是否存在"至少一对可消且 n 对全部最终可完成"；若不可完成，重新洗牌。首版可只做**上帝视角可解（每次都有可消对）**校验，全流程可完成性校验作为优化项。

## 8. 技术要点与风险

1. **路径判定**：≤2 转弯判定是核心且易错，先做 0/1/2 转分治，再覆盖边界；建议抽独立纯函数便于单测。
2. **首张选中后再选不配对卡片**：不消除、提示"不是配对"，不消耗步数（可选消耗）。
3. **死局检测**：每步消除后检查是否有可消对；无则提示洗牌，避免卡死。
4. **动画 fill 覆盖（前期踩过）**：消除动效注意 animation fill 不覆盖 `matched` 的透明/缩放终态，必要时 `animation: none !important`。
5. **成绩回写去重**：按词条 id 上报一次，配对判断用局内 key，`id` 仅回写用。
6. **中文 JSON 编码**：UTF-8 传输，避免释义乱码。
7. **词库不足**：少于所需对数时前端/C# 双重提示并降低 N。
8. **发音可用性**：`speechSynthesis` 静默降级。
9. **主题一致**：`data-theme` 与 WinForms 联动。
10. **`?mock=1` 调试**：内置示例数据浏览器直开。

## 11. 已采纳优化

### 连连看专有
1. **难度 = 转弯数上限**：把"转弯数 ≤2"改为可配置（0/1/2 转），直接作为难度档，区分度高于只改盘面大小。简单档允许相邻直连，困难档允许绕盘边或仅 1 转。
2. **死局自动洗牌**：检测到无可消对时**自动重排当前词卡**（不重新抽词）并 toast 说明，替代"弹窗提示玩家手动点洗牌"，减少打断。
3. **错题即时角标**：某词条多次被点开但"配对失败/路径不通"后，在其两张卡片上叠加淡红角标，把对局变成"薄弱词回收器"，并在结算一并汇总。
4. **路径候选提示（可选）**：点第一张后消耗 1 次提示机会，仅高亮"既是配对且路径可达"的候选卡，儿童友好。
5. **失败语义分层惩罚**：将"点错配对"与"路径不通"分开计分——点错配对扣分更多（配错比路线笨更伤记忆），路径不通仅轻微提示不重罚。

### 三款共用
6. **抽前端公共件 `Resources/Shared`**：把消消乐/翻牌/连连看重复的 `bridge()/sendToHost/toast/esc()`、发音、粒子反馈、主题变量、`{type,payload}` 消息协议、camelCase 封装统一抽取共享，各游戏只写差异。**当前代码库收益最高的一步**。
7. **统一难度/配置入口**：基类定义共识结构（如 `{difficulty, limit, hintBudget}`）由 `init` 下发，各前端复用，避免各自造难度轮子。
8. **通用成绩上报模板**：统一"每词条一条结果 + `correct` 布尔 + 局内 key 判定"协议，三款共用 DTO 与回写。
