这个问题很关键。整体来看，**技术上完全可行**，但不同模块的难度差异很大——从“一下午就能搞定”到“可能需要数月攻关”都有。

## 一、各功能模块技术难度评估

### 🟢 低难度（有成熟方案，几乎现成可用）

| 模块 | 技术方案 | 难度 | 说明 |
|------|----------|------|------|
| **Word解析** | `DocumentFormat.OpenXml`（微软官方）或 `NPOI` | ⭐ | 纯XML解析，无需安装Office。提取文本、批注、表格结构均有现成API。老版 `.doc` 可用 `NPOI` 兼容 |
| **Excel解析** | `EPPlus`（MIT协议，专为 `.xlsx` 设计） | ⭐ | 支持流式读写，百万行数据内存占用仅为OLE DB方案的1/5。列映射、增量更新都是常规操作 |
| **网页正文提取** | `HtmlAgilityPack` + `Readability.NET` | ⭐ | 两个NuGet包加起来不到200KB，核心逻辑不超过50行代码 |
| **SM-2算法** | 纯数学计算，无需第三方库 | ⭐ | Anki用的就是SM-2，实现代码约100行。SQLite存储用EF Core即可 |
| **动态表单生成** | WinForms原生 `TableLayoutPanel` + 动态控件创建 | ⭐⭐ | 根据模板定义在运行时 `new Label()` + `new TextBox()` 即可。注意用 `SuspendLayout()`/`ResumeLayout()` 避免闪烁 |

### 🟡 中等难度（有方案但需投入时间）

| 模块 | 技术方案 | 难度 | 说明 |
|------|----------|------|------|
| **PPT解析** | `Aspose.Slides FOSS`（MIT协议）或 `SlideDotNet` | ⭐⭐ | 提取文本和备注很容易。但**渲染幻灯片缩略图**是难点——OpenXML SDK不直接支持渲染，需借助 `Aspose.Slides` 付费版或 `Microsoft.Office.Interop.PowerPoint`（需安装Office） |
| **EPUB解析** | `EpubReader` 或 `VersOne.Epub` | ⭐⭐ | 本质是解压ZIP + 解析HTML。但EPUB的CSS排版复杂，提取纯文本容易，保留结构（章节嵌套）需要额外处理 |
| **PDF双向锚定** | `PdfiumViewer` + 自定义坐标映射 | ⭐⭐ | 获取点击坐标 → 映射到页面位置 → 存入数据库 → 跳转时反向还原。逻辑清晰，但需处理缩放、旋转等坐标系变换 |
| **隐式评分机制** | 事件监听 + 权重计算 | ⭐⭐ | 监听 `StayDuration`、`NoteUpdated`、`HighlightCreated` 等事件。算法本身是加权公式，不复杂。**难点在于参数调优**——权重设多少才符合人的记忆规律，需要数据验证 |

### 🔴 高难度（有技术挑战，需要专项攻关）

| 模块 | 技术方案 | 难度 | 说明 |
|------|----------|------|------|
| **PDF内存管理** | `PdfiumViewener` 资源释放 | ⭐⭐⭐ | 这是**已知痛点**。`PdfiumViewer` 的 `Bitmap` 对象若未正确 `Dispose()`，长时间使用会导致内存持续增长。解决方案：严格 `using` 包裹、分页渲染（只保留当前页±2页）、定期 `GC.Collect()` |
| **OCR中文识别** | `Tesseract.NET` | ⭐⭐⭐ | 印刷体中文识别率约85%-92%。**手写体不足65%**，复杂排版（竖排、艺术字）处理弱。替代方案：`PaddleOCR-Sharp` 通过ONNX Runtime可达92%，但模型文件较大（~100MB） |
| **跨文档语义检索** | 本地Embedding + 向量检索 | ⭐⭐⭐⭐ | 需要：①将文本转为向量（Embedding）②存储向量并做相似度检索。可用 `Build5Nines.SharpVector`+ ONNX本地模型。**挑战**：中文Embedding模型通常较大（几百MB），CPU上推理速度可能较慢。10,000篇文档的向量检索可在微秒级完成，但**生成向量**是瓶颈 |
| **知识图谱（双向关联）** | 图结构存储 + 关联推荐 | ⭐⭐⭐ | 简单方案：用 `RelatedIds` JSON字段存储关联，查询时 `WHERE Id IN (...)`。复杂方案（多层推理）需引入图数据库如 `SQLite` 的 `WITH RECURSIVE` 或嵌入式图库。推荐**先用简单方案验证** |

## 二、技术风险与缓解策略

| 风险 | 影响 | 缓解策略 |
|------|------|----------|
| **PDF内存泄漏** | 长时间使用后崩溃 | Phase 1 就建立内存监控；限制同时渲染页数；提供“清理缓存”按钮 |
| **OCR准确率不达预期** | 用户对“图片转文字”失望 | 初期标注“实验性功能”；提供手动修正入口；后续可切换PaddleOCR |
| **本地Embedding性能** | 首次向量化大量文档时卡顿 | 后台异步处理 + 进度条；支持用户选择“仅对新文档向量化” |
| **WinForms动态控件性能** | 模板字段过多时界面卡顿 | 使用 `VirtualMode`；限制单页显示字段数（超过10个用折叠面板） |
| **隐式评分算法失效** | 复习推荐不准 | 设计为“可开关”功能，用户可回退到手动评分；记录算法决策日志便于调优 |

## 三、分阶段实施建议

| 阶段 | 推荐任务 | 预估工时 | 风险等级 |
|------|----------|----------|----------|
| **Sprint 1** | Word/Excel/EPUB解析 + 统一中间件 | 3-5天 | 低 |
| **Sprint 2** | PPT文本提取（不含缩略图）+ 网页剪藏 | 2-3天 | 低 |
| **Sprint 3** | PDF双向锚定 + 坐标系映射 | 3-5天 | 中 |
| **Sprint 4** | 隐式评分 + 事件总线 | 5-7天 | 中 |
| **Sprint 5** | OCR集成 + 基础测试 | 3-5天 | 中高 |
| **Sprint 6** | 本地Embedding + 语义检索（POC） | 7-10天 | 高 |

> **总计**：核心功能约 **3-4周** 可完成POC，**完整版**（含语义检索）约 **6-8周**。

## 四、结论

> **技术上完全可行，不存在“做不了”的瓶颈。**

绝大多数功能都有成熟的开源方案可以直接使用。真正的难度不在“能不能做”，而在：

1. **PDF内存管理**——需要从第一天就建立严格的资源释放规范
2. **OCR中文识别**——需要管理用户预期，标注为“实验性功能”
3. **本地语义检索**——需要做技术选型（ONNX vs 云端API），平衡准确率和性能

如果按照“先易后难、逐步验证”的策略推进，**2个月内可以交付一个功能完整的版本**。
